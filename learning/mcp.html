LLM Tooling Protocol

MCPs

Model Context Protocol — an open standard (introduced by Anthropic in late 2024) for connecting LLM applications to external tools, data, and prompts through one uniform interface, instead of a bespoke integration per tool.

What it is

MCP is often described as “USB-C for AI tools.” It defines how an LLM application talks to a small program — an MCP server — that exposes capabilities the model can use: functions to call, data to read, and prompt templates to reuse. Any MCP-compatible application can use any MCP server without writing custom glue for it.

Why it matters

Before MCP, every assistant re-implemented every integration: one connector for GitHub, another for a database, another for a filesystem, each tied to one app. MCP turns those into reusable servers. Write a server once and it works in Claude Desktop, Claude Code, IDE extensions, and other clients. It also creates a clean security boundary — the host controls which servers connect and what the model is allowed to invoke.

Key concepts

  • Host, client, server — the host is the LLM app (Claude Desktop, an IDE). It runs one client per connection, and each client talks to exactly one server.
  • Server primitives — tools (functions the model can call, e.g. search_issues), resources (readable content such as files or records), and prompts (parameterised prompt templates the user can invoke).
  • Client primitives — sampling (a server can ask the host to run an LLM completion) and roots (the host tells the server which files/directories are in scope).
  • Transports — stdio for a local subprocess, and Streamable HTTP (with Server-Sent Events) for remote servers.
  • Messaging — JSON-RPC 2.0, with a capability negotiation handshake when the connection opens.

How it actually works

When the host starts, it launches or connects to each configured server and they exchange an initialize handshake declaring what each side supports. The client then asks the server for its catalogue: tools/list, resources/list, prompts/list. The host presents the tools to the model. When the model decides to use one, it emits a tool call; the client forwards it as tools/call; the server runs the actual code (hitting an API, reading a file, querying a database) and returns a structured result, which the client feeds back into the model's context. Resources work the same way but are read rather than executed, and prompts are expanded into messages before the conversation starts.
